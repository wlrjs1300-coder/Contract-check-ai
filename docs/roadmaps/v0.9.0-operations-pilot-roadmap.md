# v0.9.0 운영 준비 및 제한적 파일럿 로드맵

## 목표

v0.9.0의 목표는 v0.8.0까지 구현된 애플리케이션·DB·보안 기반을 다시 만드는 것이 아니라, 이를 플랫폼 중립적인 운영 경계와 절차에 연결하고 합성 데이터만 사용하는 제한적 파일럿으로 검증하는 것이다.

이 단계의 완료는 production 배포 완료, 실제 계약서 처리 승인, 실제 개인정보 처리 승인 또는 실제 외부 분석 Provider 승인을 의미하지 않는다. 배포 플랫폼과 외부 서비스는 요구사항과 검증 근거가 확보되기 전까지 확정하지 않는다.

## 기준 상태

- 기준 브랜치: `chore/v0.9.0-planning-audit`

- Git 이력상 `v0.8.0` tag가 생성됐고, main 릴리스 이력이 develop에 동기화됐다.
- Backend는 635개 테스트가 수집된다. Frontend는 현재 확인 기록상 110개 테스트가 통과했다.
- 로컬 Docker Desktop에서 MySQL 8.4, Alembic head, API, worker, `/health`, `/ready`를 사용하는 synthetic smoke가 완료됐다.
- 이 기준은 저장소 코드와 로컬 검증 기록에 대한 판단이며 특정 운영 환경의 가용성·보안·복구성을 증명하지 않는다.

상태 표기는 다음 의미로 사용한다.

| 상태 | 의미 |

| 부분 완료 | 핵심 기반은 있으나 운영 절차, 외부 연동 또는 일부 이벤트가 부족하다. |
| 미구현 | 실행 가능한 코드나 운영 구성이 확인되지 않았다. |
| 문서만 존재 | 설계·후보 문서는 있으나 구현 또는 승인이 확인되지 않았다. |

## 이미 완료된 기반

다음 항목은 v0.9.0 신규 기능으로 다시 계획하지 않는다.

- **구현 완료 — 운영 DB 연결 기반:** SQLAlchemy와 Alembic revision `0001`~`0006`, MySQL 8.4 Compose 서비스, `mysql+pymysql` driver, migration one-shot 서비스가 존재한다.
- **구현 완료 — API·worker 분리:** enqueue-only 분석 API, DB 기반 durable job, atomic claim, lease·heartbeat, stale recovery, 제한된 retry·backoff, active dedupe와 graceful shutdown이 구현됐다.
- **구현 완료 — 상태 확인:** `/health` liveness와 DB 연결·Alembic head를 확인하는 `/ready`가 분리돼 있다.
- **구현 완료 — 인증·인가:** JWT 발급·검증, 비밀번호 hash, 사용자 활성 상태와 `auth_version`, owner 기반 조회, 교차 사용자 접근의 일반 `404` 처리와 관련 공격 회귀 테스트가 존재한다.
- **구현 완료 — 저장 암호화:** AES-256-GCM envelope, canonical AAD, active/decrypt-only keyring, 암호화된 계약·추출·분석 민감 필드, HMAC 기반 email lookup, plaintext·dual-write·tamper fail-closed가 구현됐다.
- **구현 완료 — 업로드 경계:** TXT/PDF 형식·크기·페이지·추출 문자 제한, 안전한 filename 처리, 임시 원본 cleanup과 orphan sweep, PDF·이미지 OCR 경로의 제한 및 관련 테스트가 존재한다.
- **구현 완료 — 애플리케이션 경계 보호:** production 설정 fail-closed, 명시적 CORS, 프로세스 단위 rate limit, Provider 입력 PII gate, 출력 schema·참조·PII·법률 단정 표현 검증이 존재한다.
- **부분 완료 — 로깅:** JSON structured operational log, request correlation, 안전한 allowlist, HTTP·업로드·추출·rate limit·worker 이벤트와 민감 extra key 차단이 구현됐다. 외부 수집과 감사·보안 이벤트 체계는 완료되지 않았다.
- **구현 완료 — 컨테이너 실행 기반:** 비-root 공용 Python image와 API·worker·DB·migrate Compose 구성이 존재하며 실제 로컬 Docker/MySQL smoke 기록이 있다.

## v0.9.0 포함 범위

1. **공개 문서와 운영 계약 정합성**
   - 현재 API, DB, migration, worker, 암호화와 합성 Provider 상태를 공개 문서에 정확히 반영한다.
   - 환경변수를 secret/non-secret으로 분류하고 API·worker·migrate별 필수값, 기본값 금지 범위와 소유 주체를 정의한다.
   - liveness, readiness, migration, worker 상태와 배포 전후 smoke의 판정 기준을 하나의 플랫폼 중립 runbook으로 정리한다.

2. **HTTPS와 reverse proxy 신뢰 경계**
   - TLS 종단 위치, HTTP 차단 또는 redirect 책임, API가 신뢰할 proxy hop과 전달 header 정책을 배포 구조와 함께 명시한다.
   - 신뢰하지 않은 client가 forwarded header로 scheme·client identity·로그 정보를 위조하지 못하도록 proxy와 Uvicorn 설정을 명시적으로 제한한다.
   - CORS는 실제 HTTPS origin allowlist로 검증하고 proxy/body limit가 애플리케이션 업로드 제한보다 느슨하지 않도록 한다.
   - 특정 proxy 제품이나 hosting 사업자는 이 단계에서 고정하지 않는다.

3. **Secret과 암호화 키 운영 절차**
   - 환경별 secret 분리, 최소 권한 주입, build·Frontend·로그 비노출, 접근 권한 점검, 교체·폐기·복구 절차를 정의하고 synthetic secret으로 연습한다.
   - JWT, DB credential, email lookup HMAC key, data encryption keyring과 향후 Provider credential의 서로 다른 lifecycle을 구분한다.
   - active/decrypt-only 전환이 가능한 현재 runtime 경계를 사용하되, 실제 row inventory·재암호화·backup 영향 확인 없이 key를 제거하지 않는다.
   - 외부 Secret manager 또는 KMS 제품 선정과 실제 운영 key rotation은 별도 승인 전까지 확정하지 않는다.

4. **DB backup·restore와 migration 운영 절차**
   - MySQL backup 대상, 암호화·접근 통제·보존·폐기 책임과 임시 원본 경로의 backup 제외를 정의한다.
   - synthetic DB를 대상으로 backup 생성, 별도 격리 DB restore, Alembic revision 확인, `/ready` 확인과 데이터 정합성 검증을 반복 가능한 runbook으로 만든다.
   - 배포 순서는 backup/복구 가능성 확인, migration one-shot 성공, API·worker 기동 순으로 고정하고 실패 시 중단·rollback 판단 기준을 기록한다.
   - 실제 데이터 backfill, 무중단 migration, point-in-time recovery와 managed DB 제품 선정은 검증 요구가 생기기 전까지 확대하지 않는다.

5. **감사·보안 이벤트와 외부 관측성 최소 기반**
   - 기존 operational log를 유지하면서 인증 성공·실패, rate limit 차단, 권한 거부, 임시 삭제 실패, 운영 설정 실패를 목적별 audit/security event code로 구분한다.
   - actor·target은 원문 개인정보가 아닌 내부 식별자 또는 비가역 파생값만 허용하고, 인증 token·email·filename·본문·DB URL·raw exception을 금지한다.
   - 이벤트 schema와 테스트를 먼저 확정하고, 승인된 수집 경로에서 API 오류율, readiness 실패, worker 처리·재시도·stale recovery, DB 연결 실패, cleanup 실패에 대한 최소 지표와 경보를 검증한다.
   - 외부 로그 제품, 장기 보존 기간, 감사 로그의 법적 효력 또는 변경 불가능 저장소는 v0.9.0에서 임의 확정하지 않는다.

6. **제한적 합성 데이터 파일럿**
   - 앞선 운영 게이트가 통과한 후보 환경 하나에서 명백한 합성 계정·합성 계약 데이터만 사용한다.
   - HTTPS, CORS, migration, API·worker, health/readiness, 인증·ownership, 업로드 경계, 분석 job 복구, 로그 비노출과 backup/restore rehearsal을 검증한다.
   - 파일럿 접근 주체와 기간을 제한하고 종료 시 synthetic 데이터·secret·임시 자원을 정해진 절차로 폐기한다.

## v0.9.0 명시적 제외 범위

- 실제 계약서 또는 실제 개인정보를 사용하는 파일럿
- 실제 외부 분석 Provider 연결, Provider 선정·계약 또는 외부 전송 승인
- production 정식 출시, 일반 공개, SLA·가용성 보장
- 특정 cloud, hosting, reverse proxy, Secret manager, KMS, DB 또는 observability 제품의 선확정
- CI/CD 자동 배포, Kubernetes, Terraform
- WAF, antivirus, malware sandbox, archive extraction
- Redis 기반 distributed limiter와 다중 replica 전역 rate limit
- WebSocket/SSE, 작업 취소, billing, 관리자 UI
- 운영 데이터 자동 backfill, bulk re-encryption worker, 무중단 migration, multi-region, 자동 key rotation
- 장기 로그·DB 보존 기간과 법무·개인정보보호 승인 없이 정하는 삭제 SLA

## 보안 및 실제 데이터 사용 게이트

합성 데이터 파일럿은 다음 조건을 모두 충족해야 시작할 수 있다.

- 배포 후보의 HTTPS와 trusted proxy 경계가 문서화되고 위조 header·HTTP 우회 테스트를 통과한다.
- production mode가 SQLite, 누락·약한 secret, 허용되지 않은 Provider, 부적절한 CORS와 boundary 값을 fail-closed로 거부한다.
- migration이 head까지 완료되고 `/ready`가 DB 연결과 revision 불일치에 대해 실패하는 것이 검증된다.
- Secret은 승인된 Backend 전용 저장·주입 경로에 있고 source, image layer, Frontend bundle, 명령 기록과 로그에 남지 않는다.
- synthetic DB backup/restore rehearsal과 복구 후 migration/readiness 검증이 성공한다.
- 감사·보안 이벤트의 허용 필드와 금지 필드 테스트, 외부 수집 경로의 body·header 수집 차단과 접근 권한 검토가 완료된다.
- 파일럿 입력이 명백한 합성 데이터임을 운영자가 확인할 수 있고 실제 자료 업로드 금지 고지가 제공된다.

실제 계약서 또는 실제 개인정보 사용은 v0.9.0 완료만으로 허용하지 않는다. 별도 승인 전에 최소한 처리 목적·법적 근거, 보존·삭제 기간, 사용자 요청 처리, backup 재등장 방지, incident response, 접근 검토, Provider와 제3자 전송 여부를 확정하고 독립 보안·개인정보 검토를 통과해야 한다. 조건을 충족하지 못하면 합성 데이터 파일럿까지만 허용한다.

## 검증 계획

- 문서 정합성: 현재 route, 환경변수, migration head, Compose service와 문서 표를 자동 또는 수동 대조한다.
- Backend 회귀: 전체 pytest, Ruff, dependency 검사와 migration upgrade 검증을 수행한다.
- Frontend 회귀: 전체 unit test, lint와 production build를 수행한다.
- Container: image 무캐시 build, dependency import, MySQL health, migration exit code 0, API·worker restart 여부와 graceful shutdown을 확인한다.
- 상태 endpoint: 정상 DB에서는 `/health`와 `/ready`, DB 단절·migration mismatch에서는 `/ready` 503과 안전한 응답을 확인한다.
- ingress: HTTP 차단·redirect, TLS, CORS, trusted/untrusted forwarded header와 proxy upload limit을 검증한다.
- Secret: 누락·약한 값·잘못된 keyring·허용되지 않은 Provider를 거부하고 image history, Frontend artifact, 환경 출력과 수집 로그에서 secret pattern을 검사한다.
- DB 복구: synthetic backup을 별도 DB에 restore하고 revision, 암호화 envelope, ownership과 핵심 API를 검증한다.
- audit/observability: 인증 성공·실패, 권한 거부, rate limit, cleanup 실패, readiness 실패와 worker retry를 합성 재현해 event code·severity·correlation·경보를 확인한다.
- 파일럿: 합성 사용자 간 IDOR 차단, 업로드 제한, durable job 복구, 결과 조회, 로그 비노출과 종료 후 자원 폐기를 검증한다.

실제 실행하지 않은 검증은 완료로 기록하지 않는다. 실제 secret, 원문 payload, 로컬 절대 경로와 내부 로그 전문은 공개 문서나 저장소 산출물에 남기지 않는다.

## PR-5 구현 메모

JSON operational logging 호환성을 유지하며 audit/security category,
인증·권한·rate limit·readiness·cleanup·worker event, process-local metric,

보존 기간, WORM/hash-chain, 실제 on-call은 후속 범위다. 이 단계는 production
운영 완료나 실제 계약서·개인정보 사용 승인이 아니다.

## PR-6 구현 메모
