# v0.7.5 저장 암호화 migration 설계

## 기본 정보

- 버전: v0.7.5
- 브랜치: feat/v0.7.5-encryption-key-management (설계), feat/v0.7.5-scalar-field-encryption (PR-2), feat/v0.7.5-nested-json-encryption (PR-3)

## 목적과 범위

이 문서는 v0.7.5 migration 기준과 실제 적용 결과를 함께 기록한다.

기존 revision은 다음과 같다.

- `0001_current_schema_baseline`
- `0002_auth_ownership`
- `0003_scalar_field_encryption` (PR-2에서 적용 완료: `Clause.body`/`ExtractionPage.text`/`AnalysisResultItem.summary` 평문 컬럼 제거, `*_encrypted` 컬럼 전환)

## PR-3 nested JSON 구조 변경과 migration 판단

PR-3(`ExtractionPage.extra_data`의 `reviewed_text`/`final_text`/`blocks[*].text`, `Extraction.extra_data.confirmation_snapshot`의 `pages[*].final_text`/`pages[*].blocks[*].text` 암호화)은 기존 JSON 컬럼(`extra_data`)의 **내부 구조만** 바꾸는 변경이다. 컬럼 타입, nullable 여부, 제약조건은 변경되지 않으므로 새 Alembic revision을 추가하지 않았다.

대신 다음을 코드 레벨에서 구현했다.

- 합성 개발 DB를 전제로 한다. 기존 `contract_check.db`에 실제 개인정보가 있다고 가정하지 않으며, 이 작업에서 해당 파일을 자동으로 초기화·수정·삭제하지 않았다.
- decrypt 경로(`nested_json_encryption.py`)는 legacy 평문 key(`reviewed_text`, `final_text`, block의 `text`, snapshot page의 `final_text`)가 non-null로 남아 있으면 즉시 `ScalarDecryptionError`로 fail-closed 처리한다. 평문 fallback이나 dual-read는 구현하지 않았다.
- write 경로는 legacy 평문 key를 항상 제거하고 `*_encrypted` key만 남기므로(`write_extraction_page_text_field`), 이후 저장되는 row에는 평문·암호문이 동시에 존재할 수 없다.
- 결과적으로 이번 PR이 병합된 이후 새로 생성되는 row는 전부 encrypted-only이며, PR-3 병합 이전에 생성된 row(있다면)는 다음 실제 읽기 시도에서 fail-closed로 걸러진다. 개발 환경에서는 DB 초기화로 충분하다고 판단했다.
- 실사용자 데이터에 대한 자동 backfill/재암호화 스크립트는 이번 범위에 포함하지 않았다(§전략 비교의 C안과 동일하게 범위 밖으로 유지).

## 기본 전제

- 현재 개발 DB에는 실제 개인정보가 없다는 전제를 검증한다.
- 민감 row가 확인되면 migration을 fail-closed로 중단한다.
- production의 평문 dual-read fallback은 기본적으로 금지한다.
- 복호화 실패 시 평문으로 자동 fallback하지 않는다.
- migration과 테스트는 합성 데이터만 사용한다.

## 전략 비교

### A. 개발 DB 초기화 후 encrypted schema 전환

장점:

- 구현이 가장 단순하다.
- 평문 fallback이 필요하지 않다.
- 실제 개인정보가 없는 현재 단계에 적합하다.

단점:

- 기존 합성 개발 데이터가 삭제된다.

### B. 합성 데이터 one-time re-encryption

장점:

- migration 경로를 실제로 검증할 수 있다.
- 합성 fixture 성격의 개발 데이터를 보존할 수 있다.

단점:

- script의 idempotency, 부분 실패, 재실행 안전성을 검증해야 한다.

### C. 실데이터 자동 backfill

현재 범위 밖이다. 실제 데이터와 운영 승인이 없으며 부분 실패, rollback, 감사, backup 통제까지 별도 설계가 필요하다.

## 권장 전략

- v0.7.5에서는 A를 기본 전략으로 채택한다.
- 필요하면 B를 합성 데이터 전용으로 제한한다.
- C는 운영 단계 전에 별도 보안 승인을 받아야 한다.
- 보관형 실운영은 v0.7.5 migration 완료만으로 승인되지 않는다.

## 전환 불변 조건

nullable encrypted column을 검토할 경우 다음 조건을 모두 적용한다.

- plaintext와 encrypted 값의 동시 존재를 금지한다.
- exactly-one application validation 또는 DB constraint를 검토한다.
- encrypted 값이 없고 plaintext가 있는 production row는 fail-closed 처리한다.
- migration 완료 뒤 plaintext column 제거 계획을 둔다.
- 장기 dual-write를 금지한다.
- plaintext fallback에는 별도 승인, 종료 기한, telemetry, 삭제 조건이 모두 필요하다.
- 복호화 실패 시 내부 컬럼, ciphertext, nonce, key 정보, 평문을 노출하지 않는다.

## 대상과 순서

1. A/B/C/D 분류와 schema별 allowlist 확정
2. crypto core와 keyring 검증 완료
3. encrypted backing column 구조 확정
4. 개발 DB의 실제 개인정보 부재 확인
5. A 전략 적용 또는 합성 데이터 전용 B 전략 승인
6. upgrade·downgrade·재실행·부분 실패 검증
7. raw DB 평문 부재와 API 회귀 검증
8. plaintext column 제거 및 잔여 데이터 확인

## 실패 처리

- keyring, envelope, owner context가 유효하지 않으면 migration을 중단한다.
- 부분 암호화 상태를 정상 완료로 표시하지 않는다.
- 실패 시 raw SQL, 원문, 파일명, 경로, key, 내부 예외를 로그나 응답에 남기지 않는다.
- rollback 뒤에도 평문·암호문 동시 저장이나 장기 dual-write 상태가 남지 않아야 한다.
- 재실행은 합성 데이터에서 idempotency를 검증한 뒤 허용한다.

## 구현 전 미확정 사항

- revision 이름과 upgrade/downgrade 구현
- 제한된 재암호화 helper의 batch 크기와 transaction 경계

## 검증 기준

- 실제 개인정보가 있는 DB에서 fail-closed
- 합성 개발 DB 초기화 경로 통과
- 선택 시 합성 one-time re-encryption의 idempotency
- production 평문 fallback 거부
- 평문·암호문 동시 저장 거부
- migration 전후 API 계약 유지
- raw DB에서 A등급 평문 검색 실패
- downgrade와 실패 응답의 민감정보 비노출

## PR-4 migration note

- `analysis_value` encryption introduced in PR-4 changes only nested JSON content under the existing `AnalysisResultItem.extra_data` column, and is therefore handled as an application-layer schema evolution only.
- No separate Alembic migration revision is added for this PR.
- Fail-closed posture is expected for legacy rows:
  - old plaintext `analysis_value` rows
  - mixed plaintext/ciphertext rows
  - malformed or unknown-key payloads
- Kept-clear metadata fields remain unchanged: enum, severity, action priority, offsets, hashes, confidence, booleans, evidence reference fields, and normalized metadata.
- Evidence source_text/excerpt, filename/title, rotation, and re-encryption batch helper remain out of scope for PR-4.
## PR-5 migration note

  `AnalysisResultItem.extra_data` JSON column in both retained locations.
- No table or column changes occur, so no Alembic revision is required.

  unknown-key Evidence fails closed without a production fallback.

  is included. Hash/stale behavior and cleartext metadata remain unchanged.

## Scalar metadata PR-1 migration note

Revision `0004_scalar_metadata_additive` adds nullable `Text` envelope columns
for email, document filename, extraction display filename, and clause title,
plus nullable `String(64)` `email_lookup_hash`. It adds no index, unique
constraint, NOT NULL constraint, backfill, or data update. Existing plaintext
columns remain authoritative and downgrade removes only the new columns.
Migration source never reads encryption or email lookup secrets.

`EMAIL_LOOKUP_HMAC_KEY` is independent from the encryption keyring. Rotation,
application dual-read/write, production inventory, backfill, cutover, and
plaintext column removal remain later phases.

`Document.unclassified_sections` and the five normalized extracted-fact fields now use encrypted-only nested JSON values. The existing JSON columns and API shapes are unchanged, so this change requires no Alembic revision. Legacy plaintext rows fail closed and require a separately planned inventory/backfill before use. User email, filename/title fields, and rotation re-encryption are not migrated here.

- New rows stop writing top-level `extra_data["evidence"]`; the encrypted nested
  list under `analysis_value` is canonical.
- This removes a JSON key from new writes without changing a table or column,
  so no Alembic revision is required.
- Identical PR-5 duplicate rows receive read compatibility. Mismatched,
  top-level-only, and plaintext legacy shapes fail closed without fallback.
- Top-level `evidence_snapshot_hash` and `snapshot_version` remain.
- No automatic `contract_check.db` change, production backfill, cleanup helper,
  or physical deletion of historical keys is included.
